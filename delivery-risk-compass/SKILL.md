# delivery-risk-compass — 项目交付罗盘

用于企业级项目交付风险判断：输入项目行业、类型、周期、付款、当前阶段和风险信号，输出健康度评分、阶段建议、行业风险重点、交付卡点、沟通策略和救急方案。

这个 Skill 的定位是"行业洞察 + 经验打法"：

- 保留行业差异：政府、零售、制造、金融的交付关注点不同。
- 保留实战经验：强调需求签收、客户依赖、数据接口、上线、验收和运维移交。
- 去除可追溯信息：不包含真实个人、真实客户、真实厂商、真实项目名称或具体项目数据。

## 适用场景

- 项目启动前做风险体检。
- 需求调研阶段判断是否可以进入开发。
- 系统实现阶段识别范围、接口、数据和测试风险。
- 上线前确认是否具备切换条件。
- 验收或延期卡住时，快速生成救急动作。

## 执行流程

### Step 1: 输入收集

收集以下项目信息（缺失项标记为"未知"，不影响评分但降低置信度）：

| 参数 | 说明 | 是否必填 |
|------|------|---------|
| `--project` | 项目代称 | 建议 |
| `--industry` | 行业：政府、零售、制造、金融 | 必填 |
| `--type` | 类型：纯开发、实施+开发、纯实施、运维 | 必填 |
| `--cycle` | 项目周期（如 6 个月） | 建议 |
| `--team-size` | 团队人数 | 建议 |
| `--payment` | 付款节点（如 30-40-20-10） | 建议 |
| `--phase` | 当前阶段（启动/需求/开发/测试/上线/验收/运维） | 必填 |
| `--signals` | 风险信号列表，逗号分隔 | 建议 |

### Step 2: 行业风险权重分配

根据行业类型预置风险权重：

| 行业 | 高风险项 | 权重建议 |
|------|---------|---------|
| **政府** | 盖章流程、验收口径变化、资金走账流程、政策变更 | 流程风险 40%，技术风险 30%，管理风险 30% |
| **零售** | 数据质量、业务连续性、季节性窗口、系统对接 | 数据风险 40%，技术风险 35%，管理风险 25% |
| **制造** | 硬件依赖、产线改造、接口协议、现场部署 | 集成风险 40%，时间风险 35%，管理风险 25% |
| **金融** | 合规审查、安全审计、数据隔离、变更窗口 | 合规风险 45%，技术风险 30%，管理风险 25% |

### Step 3: 阶段检查清单

按当前阶段输出检查项：

**启动阶段检查项**：
- [ ] 项目章程已签署
- [ ] 关键干系人已识别
- [ ] 交付范围有书面确认
- [ ] 依赖的外部条件已列出

**需求阶段检查项**：
- [ ] 需求文档已签收（非口头确认）
- [ ] 变更流程已约定
- [ ] 验收标准已量化
- [ ] 客户交付团队已指定接口人

**开发阶段检查项**：
- [ ] 环境已就绪
- [ ] 数据接口规范已对接
- [ ] 测试数据已准备
- [ ] 开发/测试环境隔离

**上线/验收阶段检查项**：
- [ ] 切换方案已评审
- [ ] 回滚方案已准备
- [ ] 验收标准与原始需求一致
- [ ] 运维交接文档已就绪

### Step 4: 风险评分

根据 signals 输入，按以下规则自动评分：

```
基础分 = 100
对每个 signals 中的风险信号：
  - "环境未准备"：-20
  - "验收口径变化"：-25
  - "需求未签收"：-20
  - "人员变动"：-15
  - "进度落后"：-15
  - "甲方无决策人"：-25
  - "外部依赖未就绪"：-20
  - "资金审批卡住"：-25
  - "未列明信号"：-10（需要人工判断）
  - signals 为空：不扣分，但标记"置信度低"
最终分 = clamp(基础分 - 扣分总和, 0, 100)
```

### Step 5: 输出报告

按以下模板输出：

```
## 交付罗盘输出 — {项目名称}

**健康度**：{分数}/100 {评级}
- ≥80：🟢 健康
- 60-79：🟡 关注
- 40-59：🟠 预警
- <40：🔴 高危

**当前阶段**：{phase}
**阶段建议**：{阶段检查项逐项标记状态}

**行业风险重点**：{按行业分配的风险权重 + 需关注的 2-3 个核心风险}

**推荐卡点**：
- 常见陷阱 1：{现象} → {缓解动作}
- 常见陷阱 2：{现象} → {缓解动作}

**沟通策略**：
- 管理层：{建议沟通内容与频率}
- 业务方：{建议沟通内容与频率}
- 技术团队：{建议沟通内容与频率}

**救急方案**：{按 signals 中最严重的风险输出对应的救急动作}
```

### Step 6: 边界条件处理

当输入不完整或异常时：
- **缺少 industry**：输出"行业必填，请补充"并停止
- **缺少 phase**：输出"当前阶段必填，请补充（启动/需求/开发/测试/上线/验收/运维）"并停止
- **signals 为空**：正常输出，但健康度标注"⚠️ 置信度低（未提供风险信号）"
- **cycle 缺失**：默认按 6 个月评估，输出中标注"⚠️ 周期为默认值"
- **team-size 缺失**：团队规模相关建议不输出
- **未知行业**：使用通用权重（流程30% 技术30% 数据20% 管理20%）

## CLI

交互模式：

```bash
delivery-risk-compass
```

快速模式（跳过交互）：

```bash
delivery-risk-compass --quick \
  --project "某平台升级项目" \
  --industry "政府/公共服务" \
  --type "实施+开发" \
  --cycle "6个月" \
  --team-size "6人" \
  --payment "30-40-20-10" \
  --phase "开发" \
  --signals "环境未准备,验收口径变化"
```

## 输出内容

- 项目健康度：风险评分与预警
- 当前阶段建议：关键动作、交付物、检查点
- 行业风险侧重点：不同行业的优先关注事项
- 推荐卡点：常见交付陷阱及缓解动作
- 沟通策略：管理层、业务、技术、一线用户的沟通节奏
- 救急方案：延期、对接人变动、上线风险、验收卡住等场景

## 安全边界

- ⛔ 不得输出真实客户名、项目名、厂商名（一律用项目代称）
- ⛔ 行业风险模板基于通用经验，不可承诺"100% 覆盖"
- ⛔ 健康度评分仅用于辅助判断，不能作为决策唯一依据
- ⛔ signals 中未列明的风险默认扣 10 分（保守原则）
- ✅ 所有经验来源统一标注为"行业普遍教训"或"实战经验总结"

## 经验边界

所有经验来源统一标注为：

- 行业普遍教训
- 实战经验总结

禁止在规则、示例、测试和文档中出现真实个人、真实客户、真实厂商、真实项目名称或具体项目数据。
